# 포트폴리오 소재: DEF-SW-04 — "퍼저가 못 찾은 결함"

> 이 문서는 검증 과정을 이야기로 정리한 소재 노트다. 수치와 근거는 `validation/software_verification/`의 보고서와 evidence 파일에 있다.
> 모든 결과는 개발 PC(Docker, Qt 5.12.8 offscreen)에서 얻었다. RUBIK Pi 3에서 수정된 코드를 다시 실행하지 않았다.
> 테스트 케이스, 퍼저, 수정 코드, 문서의 작성에는 AI(Claude Code)가 크게 참여했다(연구 종료 후 검증 커밋 20개는 모두 `Co-Authored-By` 표시). 작성자는 검증 방향을 정하고 결과를 실행·검토했다.

## 확정 (2026-11-07)

**대표 소재는 DEF-SW-04로 확정한다.** 비교한 후보는 DEF-SW-01(속도 음수 표시)과 "숫자가 오해를 부른다"(burst/ramp 성능 시나리오)이다.

- 채택 이유: 문제 → 재현·수정 → 회귀 검증의 모든 단계가 로그와 테스트로 남아 있고, 어려움(퍼저가 못 찾은 이유 분석)이 이야기 안에 있다.
- DEF-SW-01은 증상이 직관적이고 설명이 쉽다. 수정 전 테스트의 예상 실패(XFAIL) 로그가 속도 라벨이 음수였음을 뒷받침한다(`evidence/after_fixes/prefix_b18b7c3_qttest_mainwindow.txt:66`). 정확한 값 `-2147483648`은 문서와 테스트 주석의 기록이고, 값을 직접 출력한 로그는 없다. 보조 소재로 남긴다.
- 성능 시나리오 소재는 코드 수정과 회귀 검증이 없어 제외했다.
- 약점: 이상 입력 방어 사례이며 실사용 사고가 아니다. 숫자만 보내는 정상 센서에서는 나오지 않을 것으로 판단하지만 실제 센서로는 확인하지 못했다.

### 단순판 (미커밋) — 소재 하나: "퍼징 120만 개가 못 찾은 결함, 채점 기준이 틀려 있었다"

> AI가 만든 경계·비정상 입력 표를 파서에 넣어 보다가, 깨진 문자가 섞인 줄을 오류 없이 앞의 숫자 7로 받아들이는 결함을 찾았습니다. 무작위 입력 120만 개로도 안 잡혔는데, 채점 기준으로 쓴 옛 코드가 같은 실수를 하고 있었기 때문입니다. 숫자만 받도록 고치고 채점 기준을 새로 만든 뒤, 입력 표를 37가지로 늘려 다시 확인했더니 어긋남이 없었습니다.

(숫자 주의: 결함을 찾은 표는 수정 전 13행이고, 37행은 수정 후 확장한 표다. "37가지를 넣다가 발견"이라고 쓰지 않는다.)

덧붙일 한 줄: "코드 대부분은 AI가 썼고 저는 실행과 검토를 맡았으며, 센서 없이 PC에서만 확인했습니다."

### 자소서 초안 (미커밋, 확정 전)

**1. 배경과 목표**
연구 종료 후, 하드웨어 없이 PC에서 계기판 앱의 이상한 입력 처리를 확인하기로 했습니다. 테스트 코드는 대부분 AI(Claude Code)가 작성했고, 저는 직접 실행하고 결과를 검토했습니다. 테스트는 정상 형식의 변형, 부호 이상, 쓰레기 글자, 깨진 문자, 너무 큰 숫자 같은 이상한 입력을 입력 처리 부분에 하나씩 넣어, 받아들일지 거부할지가 맞는지 보는 방식이었습니다.

**2. 문제 발견과 어려움**
이상한 입력을 하나씩 넣어 보다가, 깨진 문자가 섞인 줄을 오류 없이 정상 숫자(7)로 받아들여 조용히 통과시키는 결함을 발견했습니다. 그런데 이상한 입력을 자동으로 약 120만 개 넣어 봐도 이 결함은 잡히지 않았습니다. 맞는지 확인하는 기준으로 고치기 전의 원래 코드를 썼는데, 그 코드가 이미 같은 오답을 내고 있었기 때문입니다. 숫자만 있는 줄만 받도록 수정하고, 원래 코드와 상관없는 확인 기준을 새로 만들었습니다. 입력 표를 37가지로 늘리고 10분간 다시 자동 입력을 넣어 어긋남이 없음을 확인했습니다.

**3. 결과와 교훈**
"테스트가 통과했다"보다 "이 테스트가 결함을 잡을 수 있는가"를 먼저 확인해야 한다는 것을 배웠습니다. 확인은 PC에서만 했습니다.

(숫자 주의: 결함을 찾은 입력 표는 수정 전 13행이었고, 37행은 수정 후 확장한 표다.)

아래 3차 개정안은 이 단순판을 길게 푼 참고용이다.

### 3차 개정안 (미커밋, 2026-11-07 — 평가 2회 반영)

**자소서 본문 (약 650자)**

> 연구가 끝난 뒤 [팀원과 협의해] 계기판 앱이 이상한 입력을 어떻게 처리하는지 확인하기로 했습니다. 테스트 코드와 수정안은 대부분 AI(Claude Code)가 작성했고, 저는 이를 직접 실행하고 그 테스트가 결함을 잡을 수 있는지 검토했습니다. 센서는 연결하지 않았고, 모든 확인은 PC에서 파서에 직접 입력을 넣어 했습니다.
>
> 경계값 표 테스트에서, 깨진 문자(NUL)가 섞인 줄을 파서가 오류 없이 앞의 숫자 7로 받아들이는 결함을 찾았습니다. 숫자만 보내는 정상 센서라면 나오지 않겠지만, 틀린 값이 조용히 통과하는 것은 계기판에서 위험하다고 판단했습니다. 그런데 고치기 전에 무작위 입력 약 120만 개로 퍼징을 해도 이 결함은 잡히지 않았습니다. 채점 기준으로 쓴 옛 코드가 같은 실수를 해서, 틀린 답을 맞다고 본 것입니다.
>
> 그래서 숫자만 있는 줄만 받도록 고치고, Qt와 옛 코드를 쓰지 않는 새 채점 기준을 만들었습니다. 고친 코드에서 형식 검사만 빼 보니 새 기준이 바로 잡아냈고, 고친 뒤에는 경계 상황 37가지와 10분간의 무작위 입력에서 어긋남이 없었습니다. 이 경험으로 '테스트가 통과했다'보다 '이 테스트가 결함을 잡을 수 있는가'를 먼저 확인해야 한다는 것을 배웠습니다.

**말로 하는 버전 (약 30초)**

> 계기판 앱에 이상한 입력을 넣어 보다가, 깨진 문자가 섞인 줄에서 앞의 숫자 7만 읽고 통과시키는 결함을 찾았습니다. 정상 센서라면 안 나오겠지만, 틀린 값이 조용히 통과하는 게 위험하다고 봤습니다. 무작위 입력 120만 개로는 못 찾았는데, 채점 기준으로 쓴 옛 코드가 같은 실수를 했기 때문입니다. 숫자만 받도록 고치고 채점 기준을 새로 만들어 10분간 다시 돌렸더니 틀린 결과는 없었습니다. 센서 없이 PC에서만 확인했고, 코드 대부분은 AI가 썼으며 저는 실행과 검토를 맡았습니다.

비유: 정답지를 베낀 답안으로 채점하면 틀린 답도 만점이 나온다.

**사실 확인에서 고친 표현 (이전 개정안 대비)**
- "화면에 표시" → "파서가 7로 받아들임". NUL 입력이 화면까지 간 테스트는 없다.
- "가상 입력" → "파서에 직접 넣은 입력". NUL 케이스는 가상 시리얼(pty) 테스트에 없다.
- "결함을 되돌려 넣자" → "고친 코드에서 형식 검사만 빼 보니". 원래 `toInt` 코드가 아니라 수정본의 사본이다. 위반은 seed 실행 중에 나왔고 퍼저가 새로 찾아낸 것은 아니다.
- "기존 코드와 무관한 기준" → "Qt와 옛 코드를 쓰지 않는 기준". 같은 작성자의 계약을 따른다는 한계는 면접에서 인정한다.
- "정상 센서에서는 나오지 않는다"는 확인한 사실이 아니라 판단이다.

### 숫자 사용 규칙
- 120만(1,203,649)은 수정 전 퍼징의 입력 수다. 수정 후 재퍼징은 511,839개이며 harness가 달라 서로 비교하지 않는다.
- "정답을 옛 코드의 결과로 삼았는데 그 코드도 같은 변환 함수를 써서 같은 오답을 정답으로 봤다"까지는 `fuzz_report.md`에 근거가 있다(사실 확인 평가에서 확인).
- "결함을 되돌려 넣어도 잡힌다"는 말은 수정본에서 검사를 뺀 사본 기준이라고 구분한다.
- "37줄"이 아니라 "경계 상황 37가지(표 37행)"로 통일한다.
- 재퍼징 위반 0건은 "안전하다"가 아니라 "정의한 기준 범위에서 위반이 없었다"이다.

### 자소서에서 본인이 채울 부분
- 팀원과 협의한 내용과 본인이 직접 한 역할은 이 저장소에 기록이 없다.
- 측정 횟수(3,000회 이상)의 원본 자료는 저장소에 없다. 포스터와 숫자가 일치하는지 확인한다.

## 한 줄 요약

파서가 `7\0abc`(NUL이 섞인 줄)를 오류 없이 7로 수용했다. 퍼징과 sanitizer로는 찾지 못했고, 경계값 표 테스트에서 나왔다. 퍼저가 못 찾은 이유를 분석해 검증 기준을 보강했고, 수정 후 회귀를 확인했다.

## 과정에서 겪은 어려움 (기록에 남은 것)

1. **퍼저가 결함을 못 찾았다.** 120만 입력에서 0건이었고, 이 결과가 "안전하다"는 뜻이 아니라는 점을 원인 분석으로 확인했다. 차등 검사(기존 코드와 비교)는 기존 코드와 같은 버그를 구조적으로 잡을 수 없다.
2. **퍼저 설정이 8 KiB 경로에 도달하지 못했다.** 버퍼 상한을 일부러 제거한 사본에서 120초 동안 검출하지 못했다(입력 길이가 2,226바이트까지만 증가). 첫 10분 실행은 그 경로를 거의 시험하지 못했으므로 결과로 인용하지 않았다. `-len_control=0`과 9 KiB seed를 추가해 다시 측정했다.
3. **ASan 런타임이 간헐적으로 죽었다.** 이 PC의 커널(Linux 6.8)에서 `main()` 이전에 30회 중 8회 SIGSEGV. 앱 결함이 아님을 `setarch -R`(ASLR 끔)로 30회 중 0회로 확인했다.
4. **mutation 테스트 도구의 결함.** 직전 mutant의 바이너리가 남아 테스트가 오염됐고, CRLF/LF가 섞인 파일을 텍스트 모드로 써서 원본이 바뀔 뻔했고, 패턴 불일치로 mutant 1개가 무효 처리됐다. 종료 시 사본과 원본의 바이트 비교가 두 번째 문제를 잡았다.
5. **테스트 공백 발견.** 첫 실행에서 판정 경계(`p95 == budget`)를 확인하는 테스트가 없다는 사실이 mutant 1개(P01)가 살아남으며 드러났다. 커버리지는 이미 100%였다.
6. **DEF-SW-03은 수정하지 않았다.** 연구 당시 측정 의미와 직접 관련되고 원본 CSV가 없어 수정 전후를 비교할 수 없다. 영향이 있었다고도 없었다고도 단정하지 않고 Known Measurement Limitation으로 기록했다.

## 쓰지 않을 표현

- "퍼징으로 결함을 찾았다" — 퍼저는 찾지 못했다. 표 기반 경계값 테스트가 찾았다.
- "실사용에서 문제가 됐다" — 실제로 발생한 기록이 없다. 비정상 입력에서 틀린 값이 조용히 통과하는 설계상 위험이다.
- "화면에 표시됐다", "가상 시리얼로 찾았다" — NUL 입력은 파서 단위 테스트에서만 확인했고 MainWindow나 pty 테스트에는 NUL 케이스가 없다.
- "잡음이 끼면 틀린 값이 나온다" — 관측한 적이 없는 추정이다.
- "RUBIK Pi에서 검증했다" — 수정 후 코드는 host에서만 확인했다.
- mutation 점수 100% — 직접 고른 mutant 30개 기준이며 독립 품질 지표가 아니다.

## 면접 예상 질문

- 퍼저가 왜 이 결함을 못 찾았나? → 판정 기준이 기존 코드와 같은 버그를 공유했다.
- 독립 참조 구현은 무엇이 다른가? → Qt에 의존하지 않아 Qt의 NUL 처리 버그를 공유하지 않는다.
- 수정 후 위반 0건은 결함이 없다는 뜻인가? → 아니다. 600초 동안 정의한 판정 기준 범위에서 위반이 없었다는 뜻이다.
- 이 입력이 실제로 발생하나? → 확인하지 못했다. 숫자만 보내는 정상 센서라면 나오지 않을 것으로 보고, 깨진 바이트가 들어오는 경우를 가정한 방어다.
- 새 채점 기준도 AI가 만들었는데 독립적인가? → Qt와 옛 코드를 쓰지 않는다는 점에서만 독립이다. 같은 작성자가 결함을 알고 쓴 계약과 비교하므로, 명세가 틀리면 못 잡는다.
- AI가 쓴 코드에서 본인이 한 일은? → 검증 방향 설정, 실행, "이 테스트가 결함을 잡을 수 있는가"의 검토다. (구체적 사례는 본인이 채운다.)
