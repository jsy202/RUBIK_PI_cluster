# 포트폴리오 소재: DEF-SW-04 — "퍼저가 못 찾은 결함"

> 이 문서는 검증 과정을 이야기로 정리한 소재 노트다. 수치와 근거는 `validation/software_verification/`의 보고서와 evidence 파일에 있다.
> 모든 결과는 개발 PC(Docker, Qt 5.12.8 offscreen)에서 얻었다. RUBIK Pi 3에서 수정된 코드를 다시 실행하지 않았다.
> 테스트 케이스, 퍼저, 수정 코드, 문서의 작성에는 AI(Claude Code)가 크게 참여했다(저장소 커밋 25개 중 23개에 `Co-Authored-By` 표시, 연구 종료 후 검증 커밋 20개는 모두 해당). 작성자는 검증 방향을 정하고 결과를 실행·검토했다.

## 확정 (2026-11-07)

**대표 소재는 DEF-SW-04로 확정한다.** 비교한 후보는 DEF-SW-01(속도 음수 표시)과 "숫자가 오해를 부른다"(burst/ramp 성능 시나리오)이다.

- 채택 이유: 문제 → 재현·수정 → 회귀 검증의 모든 단계가 로그와 테스트로 남아 있고, 어려움(퍼저가 못 찾은 이유 분석)이 이야기 안에 있다.
- DEF-SW-01은 증상이 직관적이고 설명이 쉽다. 수정 전 테스트의 예상 실패(XFAIL) 로그가 속도 라벨이 음수였음을 뒷받침한다(`evidence/after_fixes/prefix_b18b7c3_qttest_mainwindow.txt:66`). 정확한 값 `-2147483648`은 문서와 테스트 주석의 기록이고, 값을 직접 출력한 로그는 없다. 보조 소재로 남긴다.
- 성능 시나리오 소재는 코드 수정과 회귀 검증이 없어 제외했다.
- 약점: 정상 센서에서는 발생하지 않는 이상 입력 방어 사례이며 실사용 사고가 아니다.

### 말로 하는 버전 (약 35초)

> 계기판 앱이 이상한 입력을 어떻게 처리하는지 확인하다가, 깨진 문자가 섞인 줄에서 앞의 숫자 7만 읽어 화면에 띄우는 결함을 찾았습니다. 정상 센서에서는 나오지 않지만, 잡음이 끼면 틀린 값이 조용히 표시되는 문제입니다. 무작위 입력 120만 개로 시험했을 땐 이게 안 잡혔는데, 정답을 옛 코드의 결과로 삼았고 그 코드가 이미 틀려 있었기 때문입니다. 줄 전체가 숫자일 때만 받도록 고치고 정답 기준을 새로 만든 뒤, 경계 상황 37가지와 10분간의 무작위 입력으로 다시 확인했습니다.

(2026-11-07 평가 반영 개정판. 면접에서는 "PC에서 가상 입력으로만 확인했다"와 AI 활용 범위를 덧붙인다.)

자소서 본문용 AI 문장: "테스트 코드와 수정안은 대부분 AI(Claude Code)가 작성했고, 저는 검증 방향을 정하고 결과를 직접 실행해 확인했습니다."

비유: 정답지를 베낀 답안으로 채점하면 틀린 답도 만점이 나온다.

### 숫자 사용 규칙
- 120만(1,203,649)은 수정 전 퍼징의 입력 수다. 수정 후 재퍼징은 511,839개이며 harness가 달라 서로 비교하지 않는다.
- "정답을 옛 코드의 결과로 삼았는데 그 코드도 같은 변환 함수를 써서 같은 오답을 정답으로 봤다"까지는 `fuzz_report.md`에 근거가 있다(사실 확인 평가에서 확인).
- "결함을 되돌려 넣어도 잡힌다"는 말은 수정본에서 검사를 뺀 사본 기준이라고 구분한다.
- "37줄"이 아니라 "경계 상황 37가지(표 37행)"로 통일한다.
- 재퍼징 위반 0건은 "안전하다"가 아니라 "정의한 기준 범위에서 위반이 없었다"이다.

### 자소서에서 본인이 채울 부분
- 팀원과 협의한 내용과 본인이 직접 한 역할은 이 저장소에 기록이 없다.
- 측정 횟수(3,000회 이상)의 원본 자료는 저장소에 없다. 포스터와 숫자가 일치하는지 확인한다.

## 한 줄 요약

시리얼 입력 `7\0abc`(NUL이 섞인 줄)가 오류 없이 7로 표시됐다. 퍼징과 sanitizer로는 찾지 못했고, 경계값 표 테스트에서 나왔다. 퍼저가 못 찾은 이유를 분석해 검증 기준을 보강했고, 수정 후 회귀를 확인했다.

## 과정에서 겪은 어려움 (기록에 남은 것)

1. **퍼저가 결함을 못 찾았다.** 120만 입력에서 0건이었고, 이 결과가 "안전하다"는 뜻이 아니라는 점을 원인 분석으로 확인했다. 차등 검사(기존 코드와 비교)는 기존 코드와 같은 버그를 구조적으로 잡을 수 없다.
2. **퍼저 설정이 8 KiB 경로에 도달하지 못했다.** 버퍼 상한을 일부러 제거한 사본에서 120초 동안 검출하지 못했다(입력 길이가 2,226바이트까지만 증가). 첫 10분 실행은 그 경로를 거의 시험하지 못했으므로 결과로 인용하지 않았다. `-len_control=0`과 9 KiB seed를 추가해 다시 측정했다.
3. **ASan 런타임이 간헐적으로 죽었다.** 이 PC의 커널(Linux 6.8)에서 `main()` 이전에 30회 중 8회 SIGSEGV. 앱 결함이 아님을 `setarch -R`(ASLR 끔)로 30회 중 0회로 확인했다.
4. **mutation 테스트 도구의 결함.** 직전 mutant의 바이너리가 남아 테스트가 오염됐고, CRLF/LF가 섞인 파일을 텍스트 모드로 써서 원본이 바뀔 뻔했고, 패턴 불일치로 mutant 1개가 무효 처리됐다. 종료 시 사본과 원본의 바이트 비교가 두 번째 문제를 잡았다.
5. **테스트 공백 발견.** 첫 실행에서 판정 경계(`p95 == budget`)를 확인하는 테스트가 없다는 사실이 mutant 1개(P01)가 살아남으며 드러났다. 커버리지는 이미 100%였다.
6. **DEF-SW-03은 수정하지 않았다.** 연구 당시 측정 의미와 직접 관련되고 원본 CSV가 없어 수정 전후를 비교할 수 없다. 영향이 있었다고도 없었다고도 단정하지 않고 Known Measurement Limitation으로 기록했다.

## 쓰지 않을 표현

- "퍼징으로 결함을 찾았다" — 퍼저는 찾지 못했다. 표 기반 경계값 테스트가 찾았다.
- "실사용에서 문제가 됐다" — 정상 센서 값으로는 발생하지 않는다. 비정상 입력에서 틀린 값이 조용히 표시되는 설계상 위험이다.
- "RUBIK Pi에서 검증했다" — 수정 후 코드는 host에서만 확인했다.
- mutation 점수 100% — 직접 고른 mutant 30개 기준이며 독립 품질 지표가 아니다.

## 면접 예상 질문

- 퍼저가 왜 이 결함을 못 찾았나? → 판정 기준이 기존 코드와 같은 버그를 공유했다.
- 독립 참조 구현은 무엇이 다른가? → Qt에 의존하지 않아 Qt의 NUL 처리 버그를 공유하지 않는다.
- 수정 후 위반 0건은 결함이 없다는 뜻인가? → 아니다. 600초 동안 정의한 판정 기준 범위에서 위반이 없었다는 뜻이다.
- 이 입력이 실제로 발생하나? → 정상 센서로는 발생하지 않는다. 잡음이나 오류로 깨진 바이트가 들어올 때의 방어다.
