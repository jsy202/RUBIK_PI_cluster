# Performance Report — RUBIK Pi Qt Digital Cluster

## Part 1. Historical Result (연구 당시, RUBIK Pi 3)

README에 따르면 포스터/논문에 평균 지연시간과 jitter 값이 제시되었다. 그러나 **그 수치는 이 저장소에 기록되어 있지 않다.** 따라서 이 보고서는 연구 당시 수치를 인용, 재현, 재해석하지 않는다. 연구 당시 측정 정의(jitter = 모집단 표준편차, `t_frame − t_in`)는 그대로 유지했다.

## Part 2. Post-project Validation Result (2026-10-01, 이 PC)

> **동일 조건 비교 아님.** 아래 수치는 RUBIK Pi 3가 아닌 개발 PC에서 얻은 것이다. 하드웨어, OS, 그래픽 스택, 입력원이 모두 다르다.

### 환경

| 항목 | 값 |

| CPU | AMD Ryzen 5 5500GT (12 threads), x86_64 |
| 실행 | Docker, `Dockerfile.test` 이미지(Ubuntu 20.04, Qt 5.12.8, GCC 9.3, `-O2`) |
| Qt 플랫폼 | **offscreen.** 실제 화면 출력 없음 |
| 입력 | `CLUSTER_SIMULATE`(기존) 또는 `CLUSTER_REPLAY_FILE`(추가). 시리얼 하드웨어는 쓰지 않음 |
| 코드 | `0a77c37`과 같은 작업 트리 |
| 실행 시간 | 시나리오당 약 30 s(`timeout` 32 s), 3회 반복 |
| 원시 데이터 | `validation/perf_results/run{1,2,3}/<scenario>/latency_metrics_*.csv`, `summary.json`, `app.log` |
| 재현 | `./scripts/run_perf_scenarios.sh` (`OUT=`, `DUR=` 변경 가능) |

측정 구간은 `measurement_boundary.md`에 정의되어 있다. 요약하면 앱이 샘플을 받아들인 시점부터 rpmLabel의 paintEvent가 끝난 시점까지이며, 시리얼 전송과 물리 표시는 포함하지 않는다.

판정 기준(REQ-PERF-001): **p95 ≤ 33.3 ms(soft budget).** hard deadline이 아니다.

### 관찰 (측정된 사실)

1. **기존 시뮬레이션(50 Hz 입력):**
   - p95 20 ms, max 22 ms로 PASS.
   - 샘플의 약 40 %(630~636 / 약 1598)가 로그되지 않았다. 계산상 기대값은 1 − 30.3/50 ≈ 39.4 %이고 측정값과 일치한다.
   - **지연 통계는 표시된 샘플에 대해서만 계산된다.**
2. **고정값(2500):** 3회 모두 로그는 1건이었다. 같은 값은 `setText` 없음 → repaint 없음 → 로그 없음이다. 정속 구간에서는 지연 표본이 사실상 없다는 뜻이다.
3. **급변(0/8000, 20 ms 교대):**
   - 로그된 값은 약 100 ms마다 한 번씩만 바뀌었다(CSV에서 확인).
   - 입력은 25 Hz로 교대하지만, 33 ms UI 주기로 샘플링하면서 **aliasing이 일어나 화면은 실제 입력과 다른 저주파 패턴을 보인다.**
   - 약 79 %(1178 / 1497)가 로그되지 않았다.
4. **입력 주기 = UI 주기(33 ms):**
   - 3회 모두 **FAIL**(p95 34 ms, 900건 중 440~452건이 33.3 ms 초과).
   - 두 타이머가 같은 주기로 위상 고정되어, 샘플이 flush 직후에 도착하고 거의 한 주기를 기다린다(CSV: `t_in=33 → t_frame=67`).
   - 앱이 느려서가 아니다. **측정 정의에 throttle 대기가 포함되어 있고, 입력 위상이 나쁘면 33.3 ms budget을 구조적으로 넘을 수 있다**는 것을 보여 준다.
5. **버스트(1 kHz):**
   - p95 2 ms로 PASS. 그러나 약 97 %(약 28,800 / 29,800)가 표시도, 로그도 되지 않았다.
   - 지연 수치만 보면 "가장 빠른" 시나리오처럼 보이지만, 대부분의 입력이 버려졌다. **지연 지표만으로는 성능을 판단할 수 없다**(REQ-PERF-002).
6. **반복성:** 3회 사이의 차이는 p95 기준 0 ms, max 기준 1~2 ms 이내였다.

### 해석상 주의

- offscreen 플랫폼은 실제 윈도 시스템의 합성(compositing)과 vsync를 포함하지 않는다. RUBIK Pi에서 실제 디스플레이를 쓰면 paint 스케줄링이 다를 수 있다.
- PASS/FAIL은 정의된 측정 구간과 이 환경에 대한 판정이다. 연구 당시 RUBIK Pi 결과의 PASS/FAIL을 뜻하지 않는다.
- 위의 1~5는 앱 코드의 결함이라기보다 **설계(30 Hz 최신값 표시)와 측정 정의의 성질**이다. 이번 검증에서는 동작을 바꾸지 않고, 보고 방식(로그되지 않은 샘플 수, 측정 구간 정의)을 보완했다.
