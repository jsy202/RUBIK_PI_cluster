# 상황 설명서: 2025-10-21 간헐 RPM 튐

README의 보고서에 담지 못한 배경을 자세히 적은 문서다. 내용을 세 가지로 구분한다.

- **코드로 확인한 사실**: 저장소 코드를 읽어서 확인한 것
- **증언**: 작성자와 팀원이 겪었다고 말한 것 (이 저장소로 증명할 수 없음)
- **추정 / 모름**: 근거는 있지만 측정으로 확인하지 못한 것

`[작성자 확인]` 칸은 작성자만 아는 정보다. 채우기 전에는 면접에서 구체적인 값이나 횟수를 단정하지 않는다.

## 1. 시스템이 하는 일 (코드로 확인한 사실)

```
센서 → 아두이노 → UART(9600 8N1, 수신 전용) → Qt 앱 → 30 Hz 화면 갱신 → RPM 라벨, CSV 기록
```

- 아두이노가 `2500\n`처럼 줄 단위 10진수로 RPM을 보낸다.
- 앱은 한 줄을 읽어 "정수 형식인가"만 확인하고, 통과하면 그대로 받아들인다.
- 화면은 33 ms마다 가장 최근에 받은 값 하나만 갱신한다. 그 사이에 들어온 값은 덮어쓰인다.
- 속도 표시는 화면에 표시된 RPM에서 계산한 값이라, RPM이 튀면 속도도 같이 튄다.
- 이 경로에는 체크섬, 순번, 타임스탬프, 수신 타임아웃이 없다.
- 버려진 줄은 개수도 내용도 남지 않는다.

## 2. 일어난 일 (증언)

- 2025-10-21, 팀원이 디지털 클러스터의 RPM이 순간 튀었다가 정상으로 돌아오는 것을 봤다.
- 이후에도 1~2번 더 관측됐다. 아주 가끔 일어났다.
- 작성자는 같은 시스템을 돌렸을 때 한 번도 보지 못했다.
- 소프트웨어를 디버깅했지만 원인을 찾지 못했다.

## 3. 왜 단서가 없었나 (코드로 확인한 구조)

1. **로그가 화면 기준이다.** CSV는 화면이 그려진 직후에만 한 행씩 쓴다. 지연 측정이 목적이라 그렇게 설계됐다.
2. **샘플이 덮어쓰인다.** 33 ms 안에 들어온 값은 마지막 하나만 남는다. 튄 값이 그 사이에 끼면 화면에도 로그에도 남지 않는다.
3. **버려진 줄에 흔적이 없다.** 파서가 줄을 버려도 개수나 내용을 기록하지 않는다.
4. **순번이 수락된 샘플만 센다.** 버려진 줄은 순번에 빈칸도 만들지 않아서, 없어진 줄을 로그에서 알아낼 수 없다.

그래서 튄 값이 화면에 한 번 올라갔다가 정상 행처럼 기록되거나, 아무 흔적 없이 사라질 수 있다. 직접 돌려 본 사람이 "문제 없음"이라고 말해도 모순이 아니다.

## 4. 작성자가 한 일 (순서)

1. **소프트웨어 디버깅.** 깨끗한 입력에서는 앱이 값을 바꾸지 않았다. 문제는 앱 안이 아니라 들어오는 데이터 쪽일 것으로 봤다.
2. **형식 검사.** 튄 값이 정상 정수라서 통과했다. 한 글자가 바뀐 `3500`은 숫자로서 아무 문제가 없다.
3. **변화 폭 제한.** 직전 값과 차이가 크면 거르는 방식을 시도했다. 폭을 좁히면 정상 노이즈와 가속까지 버리고(14%), 넓히면 작은 오염이 통과한다. 값만 봐서는 오염과 실제 변화를 구분할 수 없다는 결론에 닿았다.
4. **CRC-8 임시조치.** 수업에서 배우던 CAN이 프레임마다 검산값을 쓰는 방식에서 착안해, 줄마다 CRC-8을 붙였다. (착안 과정은 작성자 증언)
5. **효과 확인.** 오염을 일부러 주입해서 검산값이 틀린 값을 걸러내고 기록을 남기는지 확인했다.

## 5. 원인 추정과 근거

**추정: 아두이노에서 보드까지의 UART 구간 회로 문제(배선, 접촉, 접지, 노이즈).** 측정으로 확인하지 못했다.

근거:
- 깨끗한 입력에서 앱은 값을 바꾸지 않았다. 문제는 입력 쪽에 있다.
- 이 구간은 UART라서 오류를 걸러 주는 장치가 없다.
- CAN 구간이었다면 CAN 자체가 CRC와 오류 프레임으로 걸러내서 앱까지 오지 않았을 것이다. 그래서 CAN은 원인 후보에서 뺐다.

배제하지 못한 것:
- 센서 입력이나 아두이노 계산에서 이미 틀린 값이 만들어졌을 가능성. 이 경우 검산값은 맞게 계산되어 통과한다.
- 접촉 불량이 아닌 다른 간헐 원인.

## 7. 왜 임시조치인가

- 근본 원인은 회로로 추정되는데 간헐적이라 바로 잡지 못했다. 그동안 틀린 값이 화면에 나가지 않게 막는 격리 조치로 CRC를 넣었다.
- 걸러진 줄의 시각과 원본 바이트가 기록으로 남아서, 회로를 점검할 때 단서가 된다.
- 근본 대책 후보: 배선과 접지 점검, 차폐, 실제 아두이노 송신 코드에도 검산값 적용.
- 한계: 걸러진 순간에는 이전 값이 유지된다. 송신 전에 틀린 값은 못 막는다.

## 9. 예상 질문과 정직한 답

**Q. 실제로 몇 번 발생했나요?**
팀원이 1~2번 봤다고 들었고, 저는 직접 보지 못했습니다. 정확한 횟수와 발생 시각 기록은 없습니다. 그래서 오염 주입으로 재현했습니다.

**Q. 왜 회로 문제라고 보나요?**
깨끗한 입력에서는 앱이 값을 바꾸지 않았습니다. 이 구간은 UART라 오류를 걸러 주는 장치가 없습니다. 다만 측정으로 확인한 건 아니고 추정입니다.

**Q. CAN은 이미 CRC가 있는데 왜 또 넣었나요?**
이 시스템의 경로는 CAN이 아니라 UART입니다. UART에는 그런 보호가 없어서, CAN 같은 검산값 방식을 직접 추가했습니다.

**Q. 변화 폭 제한으로는 안 되나요?**
시도했습니다. 폭을 좁히면 정상 값을 14% 버리고, 넓히면 끝자리가 바뀐 오염이 통과합니다. 값만으로는 구분이 안 됩니다.

**Q. CRC로 모든 문제가 해결됩니까?**
아닙니다. 전송 중 변조만 막습니다. 센서나 아두이노에서 이미 틀린 값이 만들어졌다면 통과합니다. 근본 원인은 회로 점검이 필요합니다.

**Q. 시뮬레이션 수치는 어디까지 믿을 수 있나요?**
오염 종류와 비율은 제가 가정한 모델이고, 실제 UART 오류 분포와 다를 수 있습니다. 걸러내는 원리와 로그 구조의 문제는 코드와 시험으로 확인했지만, 현장 발생률은 모릅니다.
