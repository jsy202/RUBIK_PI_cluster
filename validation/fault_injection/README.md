# 간헐 RPM 튀는 값: 재현, 한계 확인, 임시조치(CRC) 보고서

작성 2026-11-23. 2025-10-21에 처음 관측된 현상을 대상으로 한다.

> **먼저 읽을 것.** 아래의 현상 설명(1절)은 작성자와 팀원의 증언이다. 2~6절의 모든 수치는 **오염 주입 시뮬레이션** 결과이며 실제 현장 로그가 아니다. 오염 발생률(32,400프레임에 1회)은 측정값이 아니라 실험 설정값이다. 회로 원인은 **추정**이고 하드웨어 측정으로 확인하지 못했다.

## 요약

| 항목 | 내용 |
|---|---|
| 현상 | 2025-10-21 팀원이 RPM 값이 순간 튀는 것을 관측. 이후 1~2회 더. 작성자는 직접 보지 못함 |
| 당시 상태 | 줄마다 "정수인가"만 확인. 거부된 줄과 덮어쓰인 샘플은 흔적이 없음 |
| 시도했지만 한계가 확인된 검증 | 형식 검사(오염 106건 수용), 변화 폭 제한(폭 200은 19건 통과, 폭 100은 정상 값 14% 손실) |
| 임시조치 | 줄마다 CRC-8 검산값을 붙이고, 불일치하면 버린 뒤 마지막 정상값을 유지하고 사유와 원본 바이트를 기록 |
| 효과(시뮬레이션) | 틀린 값 수용 106건 → 0건. 실제 앱 시험에서 화면에 오른 틀린 값 31건 → 0건 |
| 남은 과제 | 회로 근본 원인 미확정. CRC는 송신 전 단계에서 이미 틀린 값을 못 막음 |

## 1. 현상 (증언)

- 2025-10-21, 디지털 클러스터의 RPM이 순간 튀었다가 정상으로 돌아오는 현상을 팀원이 관측했다.
- 이후에도 1~2회 더 관측됐다. 작성자가 같은 조건에서 돌렸을 때는 나타나지 않았다.
- 소프트웨어를 디버깅했지만 원인을 찾지 못했다.
- 당시 로그(`latency_metrics_*.csv`)에는 화면에 그려진 샘플만 남는다. 거부된 줄, 33 ms 안에 덮어쓰인 샘플, 파서가 버린 줄은 기록되지 않는다.

## 2. 소프트웨어 쪽 확인

- 오염 주입 없는 프레임에서 앱은 송신값을 그대로 표시했다. 실제 앱 시험에서 틀린 값으로 표시된 31건은 전부 주입 지점 2프레임 이내였다(`results/e2e_plain/summary.json`).
- 파서 수준 시뮬레이션의 깨끗한 입력(900만 프레임)에서 정상 값을 잘못 버린 경우는 형식 검사, 변화 폭 200, CRC 모두 0건이었다.
- 따라서 깨끗한 입력에서는 앱이 값을 만들어 내지 않는다고 판단했고, 문제는 들어오는 데이터 쪽에 있다고 보았다.

## 3. 재현 방법 (가정 포함)

- 입력: 앱 시뮬레이션과 같은 모양의 RPM(2500 ± 1700 사인파, 노이즈 ±60), 20 ms 주기, 줄 단위 전송.
- 오염: 비트 반전, 글자 삭제, 글자 삽입을 같은 비율로 섞고, 위치는 무작위. 시드 고정(20261123). **이 오염 모델은 가정이다.**
- 발생률: 기준 설정은 32,400프레임에 1회(20 ms에서 약 10.8분). 측정값이 아니다.
- 두 수준: (A) 파서 수준 대규모 시뮬레이션, (B) 실제 앱을 가상 시리얼(PTY)로 구동하는 시험. B는 실시간이라 오염률을 100프레임에 1회로 가속했다.
- 33 ms 쓰로틀 때문에 주입된 오염이 모두 화면에 보이지는 않는다. A에서는 이를 반영해 "화면 노출"을 계산했다.

## 4. 시도했지만 한계가 확인된 검증

### 4-1. 형식 검사 (당시 구현)
정수 형식인지만 확인한다. 한 글자가 바뀐 `3500`은 정상 정수라서 통과한다. 줄바꿈이 사라지면 두 줄이 붙은 `8002500`도 통과한다.

### 4-2. 변화 폭 제한
직전 정상값과의 차이가 폭을 넘으면 거른다. 폭은 시뮬레이션 파형의 정상 최대 변화(약 165)에서 200으로 잡았고, 100도 비교했다. (알고리즘은 임시 구현: 3회 연속 거부면 수용)
- 폭 200: 변화가 작은 오염(끝자리 비트 반전 등)을 못 거른다.
- 폭 100: 오염은 거의 그대로 남고, 정상 노이즈와 가속을 14% 버린다.
- 어느 폭에서도 둘을 동시에 막지 못한다. 값만 봐서는 오염과 실제 변화를 구분할 수 없다.

## 5. 임시조치: 줄별 CRC-8

- 형식: `값,HH\n` (HH = 값 문자열의 CRC-8, 다항식 0x1D, 초기값 0). 앱은 `CLUSTER_PROTECT=1`일 때만 이 형식을 쓰고, 기본 동작은 그대로다.
- 불일치, 형식 오류, 길이 초과인 줄은 버린다. 화면은 마지막 정상값을 유지한다.
- 사유와 원본 바이트(16진)를 `reject_log_*.csv`에 남긴다.
- CAN과 AUTOSAR E2E가 쓰는 검산값 방식에서 착안했다. E2E 프로파일을 구현하거나 준수한 것이 아니다.
- 구현: `framecheck.h`, 단위 시험 `tests/tst_framecheck`(CRC 공개 확인값 0x37 일치, 모든 단일 비트 반전과 삭제에서 틀린 값 0건), 앱 통합 시험 `tst_mainwindow`.

## 6. 결과 (모두 시뮬레이션)

### 6-1. 파서 수준 (50시간 분량, 900만 프레임, 오염 247건: 비트 반전 78 / 삭제 82 / 삽입 87)

| 방식 | 틀린 값 수용 | 화면에 실제 표시 | 정상 값 오폐기(깨끗한 입력) | 거부 기록 |
|---|---|---|---|---|
| 1. 형식 검사만 | 106 | 64 | 0 | 0 |
| 2a. 변화 폭 200 | 19 | 10 | 0 | 89 |
| 2b. 변화 폭 100 | 18 | 13 | 1,233,991 | 1,640,953 |
| 3. CRC-8 | **0** | **0** | 0 | 245 |

원자료: `results/parser_sim_32400.txt`.

### 6-2. 실제 앱, 가상 시리얼 (10,000프레임, 오염 104건: 삭제 39 / 비트 반전 36 / 삽입 29, 100프레임에 1회로 가속)

| 방식 | 화면에 그려진 틀린 값 | 거부 기록 |
|---|---|---|
| 형식 검사만(보호 끔) | **31** | 0 |
| CRC-8(보호 켬) | **0** | 103 (crc 62, format 41) |

거부 기록이 103건인 이유: 한 건은 16진 두 글자 중 하나가 소문자로 바뀐 것으로, 값은 그대로라서 수용됐다. 원자료: `results/e2e_*/`.

### 6-3. "가끔만 보인다"의 해석
파서 수준 시뮬레이션에서 오염의 약 26%(64/247)만 화면에 올랐다. 이 비율이면 화면에서 보이는 오염은 약 47분에 1번이고, 10분 관찰에서 한 건도 못 볼 확률은 약 81%다. 이는 설정한 오염률과 오염 모델에 의존하는 계산이다.

## 7. 한계와 남은 과제

- **회로 원인은 미확정이다.** 추정은 아두이노에서 보드까지의 UART 구간(배선, 접촉, 노이즈)이지만 측정하지 못했다. 거부 기록의 시각과 원본 바이트가 회로 점검의 단서가 된다.
- **CRC는 전송 구간의 변조만 막는다.** 센서 입력이나 송신 쪽에서 이미 틀린 값이 만들어졌다면 검산값이 맞아서 통과한다.
- **걸러진 줄의 순간은 값이 이전 값으로 유지된다.** 손실 자체는 막지 못한다.
- PTY는 실제 UART가 아니고, 오프스크린 렌더링은 실제 화면이 아니다. 오염 모델과 발생률은 가정이다.
- 33 ms 동안의 깜빡임이 사람 눈에 보이는지는 증명하지 못했다. "그려졌다"까지만 말할 수 있다.
- 송신 쪽은 아두이노가 아니라 PC 스크립트로 대신했다(저장소에 스케치가 없음). 실제 보드 송신 코드에도 CRC를 넣어야 현장에서 효과가 난다.
- 변화 폭 제한의 구현은 비교용 임시 구현이다.
- 입력 중단과 재연결(타임아웃)은 검증하지 않았다.
