# Input-rate Sweep — Analysis (Post-project Validation, 2026-10-02)

> **하드웨어 검증이 아니다.** 측정 환경: 개발 PC(AMD Ryzen 5 5500GT, x86_64), Docker(`Dockerfile.test`, Ubuntu 20.04, Qt 5.12.8), Qt **offscreen** 플랫폼, `CLUSTER_REPLAY_FILE` 입력. RUBIK Pi 3, Arduino, 실제 디스플레이는 사용하지 않았다.
> 측정 구간: **sample acceptance(`t_in`) → rpmLabel `paintEvent` 완료(`t_frame`)**. UART 전송과 물리 표시는 포함하지 않는다([measurement_boundary.md](../measurement_boundary.md)).
> 등급 A(실제 실행). 원시 데이터: [raw_results.csv](raw_results.csv)(run별), [summary.csv](summary.csv)(rate별), `runs/`(앱 CSV + app.log), `inputs/`(replay 파일).

## 방법

- rate별로 입력 15 s 분량의 서로 다른 RPM 값(1000, 1001, …)을 넣었다. 값이 모두 달라서 표시될 때마다 repaint가 일어난다.
- run 시간은 25 s(`timeout`)이고, 21개 run 모두 replay를 끝까지 재생했다("Replay finished"). 그래서 accepted = input이다.
- QTimer는 정수 ms 단위다. 명목 rate → 주기: 10 → 100 ms, 30 → 33 ms(30.3 Hz), 60 → 17 ms(58.8 Hz), 100 → 10 ms, 200 → 5 ms, 500 → 2 ms, 1000 → 1 ms.
- 실측 입력 rate는 CSV의 `t_in`으로 계산했다.
- 각 조건 3회 반복. 형식은 평균 [최소–최대].
- 실행: `REPS=3 ./scripts/rate_sweep.sh && python3 scripts/rate_sweep_analyze.py`

## 1. Input Rate vs Drop Ratio

| 명목 rate | 10 | 30 | 60 | 100 | 200 | 500 | 1000 |
|---|---|---|---|---|---|---|---|
| drop ratio | 0 % | 0 % | 48.4 % | 69.7 % | 84.8 % | 93.9 % | 96.8 % |

입력 rate가 UI flush rate(약 30.3 Hz, 33 ms)를 넘으면, 한 flush 주기 안에 들어온 샘플 중 마지막 하나만 표시되고 나머지는 덮어쓰인다. 측정값은 1 − 30.3 / 실측 rate와 거의 같다(예: 100 Hz → 69.7 %, 기대 69.7 %; 200 Hz → 84.8 %, 기대 84.9 %). logged 샘플 수는 입력 rate와 무관하게 약 455개(≈ 30.3 Hz × 15 s)로 일정했다.

## 2. Input Rate vs p95 Latency

| 명목 rate | 10 | 30 | 60 | 100 | 200 | 500 | 1000 |
|---|---|---|---|---|---|---|---|
| p95 (ms) | 32 | **34** | 17 | 10.3 | 5 | 3 | 2 |
| 33.3 ms 초과 | 1–3 | **223–236 / 454** | 0 | 0 | 0 | 0 | 0 |
| p95 ≤ 33.3 판정 | PASS | **FAIL** | PASS | PASS | PASS | PASS | PASS |

- **10 Hz:** 샘플이 flush 주기 안의 임의 위치에 도착하므로 대기 시간이 0~33 ms에 고르게 퍼진다(p50 19 ms, p95 32 ms).
- **30 Hz:** 입력 주기와 flush 주기(33 ms)가 같아 위상이 고정된다. 샘플이 flush 직후에 도착해 거의 한 주기를 기다린다(p50 33.7 ms, 약 절반이 33.3 ms 초과).
- **60 Hz 이상:** "표시된" 샘플은 flush 직전에 도착한 최신 샘플이다. 그래서 대기 시간이 입력 주기 이하로 짧아지고, p95는 입력 주기와 거의 같아진다(17 ms 주기 → 17 ms, 10 → 10.3, 5 → 5, …).

## 3. 해석 (검증 관점)

**latency는 낮아지는데 drop ratio는 높아지는 조건이 실제로 있다.** 60 Hz부터 1000 Hz까지 p95는 17 → 2 ms로 낮아졌지만, drop ratio는 48 → 97 %로 높아졌다.

이 결과는 성능 개선이 아니다. 다음 두 가지를 확인한 것이다.

1. 이 시스템의 지연 통계는 **표시된(painted) 샘플에 대해서만** 계산된다. 입력이 많아질수록 "가장 최근 샘플만 표시"되는 선택 효과 때문에 지연이 작게 측정된다.
2. 따라서 **Latency 단독 지표가 실제 처리 품질(입력 중 얼마나 표시되었는가)을 충분히 나타내지 못할 수 있음을 확인했다.** 성능 판정에는 지연과 함께 drop ratio(또는 logged/accepted)를 같이 보고해야 한다(REQ-PERF-002).

반대로, 표시 지연 측면에서 가장 나쁜 조건은 고부하가 아니라 **입력 주기가 UI 주기와 같은 30 Hz**였다(PASS/FAIL 기준을 넘은 유일한 조건). 이는 throttle 대기가 측정 구간에 포함되는 설계의 성질이다.

## 4. 한계

- PC, Docker, offscreen 결과이며 RUBIK Pi 3 결과가 아니다. 실제 디스플레이의 합성과 vsync는 포함되지 않는다.
- 입력은 replay 타이머로 넣었고 시리얼 수신 경로를 거치지 않았다. 1 kHz 명목 조건의 실측은 938 Hz였다(QTimer 1 ms 한계).
- 각 조건 15 s × 3회. 반복 간 차이는 p95 기준 0~1 ms, max 기준 최대 14 ms(500 Hz: 17–31 ms)였다.
- drop은 "설계상 최신값만 표시"의 결과이며, 이 조건에서 앱의 결함으로 판단하지 않는다.
